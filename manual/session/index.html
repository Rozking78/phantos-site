9Session & network

A show is a session: one Babel hub, and every console, media node and display node that joins it. Command talks only to Babel. Babel talks to the gear.

Am I in?

The lamp at the top left of the screen. Green and Broker means you are in a session; red and offline means you are alone. Sessions shows the detail — Babel's address and identity, this console's operator name, role and domain, and how many apps and devices are in the session. Settings ▸ Comms is the same panel from the settings side.

The desk is standalone until it joins

Nothing leaves this machine before a session forms. If a light is not moving, check the lamp first: an offline console is doing everything you asked, locally, to nobody.

How do I get this console into the show?
  1. Open Sessions.
  2. Type Babel's LAN address into the Babel IP field and press Connect. Get the address off Babel's own Sessions window; there is no discovery to wait for and it is never a loopback address.
  3. Fill in your Operator name so the rest of the session knows whose values are whose.
  4. That is all. There is no Join button — once you reach Babel, every console on that Babel converges on the same session by itself. Create Session is there for naming one; Leave Session steps out.

Each domain gets an output priority, 0 to 200, default 100: higher wins, and equal priorities merge — highest-takes-precedence on intensity, latest-takes-precedence on everything else.

Executors in a session

In a session, Babel runs the executors. Tapping an executor tile, go or release sends Babel a request; the tile lights or clears when Babel reports that the executor is running or idle — not when you tapped. If Babel refuses the request (another console holds that executor), the status line says so and the tile stays exactly as it was. Undoing a go or a master move in a session never rewrites the session's playback state either: what Babel reports is what every tile shows. Offline, the desk runs its own executors and the tiles follow them directly.

Two consoles, two different shows

Values merge. Patches never do. A session runs one show, and joining a session can never blend your patch with somebody else's.

When you reach a Babel that is already running a different show from the one loaded here, the console seals the show document in both directions and tells you on the status line. While it is sealed, nothing crosses: no fixture, preset, group or executor comes in from the session, and none of yours goes out. Your patch stays exactly as you left it, and so does theirs. Values, executors and everything else on the wire keep running normally — only the show document is held.

You have three ways out, and the console will not choose for you:

ChoiceWhat it does
show adoptTake the session's show. The host serves it, the console verifies it and replaces what is loaded here. Once you are on the same show, the seal lifts by itself and the two consoles resync normally.
show pushKeep yours and publish it into the session anyway. This does not remove the session's fixtures — no console can withdraw another console's rows — so the session then holds both. Use it when you know that is what you want.
session leaveStep out of the session. Nothing was exchanged.

show gate reads the state back at any time — which show the session runs, which one is loaded here, and whether the seal is on.

It does not matter which console joined which. Every console on a session says which show it is running, so both machines make the same check and reach the same answer — neither can be pulled into the other's show by the other's behaviour.

An empty console is not sealed: with no show loaded there is nothing to blend, so it simply takes the session's show, as it always has.

Two consoles, the same show

Same show, one rig. A fixture belongs to the show once, and joining a session can never give you a second copy of it.

When both consoles are on the same show the seal is off and they resync normally — that is the whole point of running two of them. What the console will not do is take a fixture it already has. Every patched fixture carries a permanent identity of its own, kept through renumbering, readdressing and renaming, and the console matches on that rather than on the fixture number. So if the two copies of the show have drifted apart — one machine renumbered, or was edited while the other was offline — the session's copy of a fixture you already hold is simply not taken, and your rig does not appear twice. A fixture the other operator genuinely added still arrives as normal.

The status line says how many rows were held, and show gate reads it back.

A console that takes the show from the session (RFR)

An RFR console is a second pair of hands on somebody else's show. It never contributes show data to the session — not its patch, not its presets, groups, executors or timecode presets.

Launch a machine as Command RFR and it takes the show from the session and leaves it there. Whatever show that machine happened to have open stays on its own disk and never reaches the session: it cannot publish it, cannot re-publish it on reconnect, and cannot withdraw anybody's rows. show push does not apply — there is no override, because there is no case where an RFR should be pushing a show at anyone.

Everything you actually use it for works normally: selecting fixtures, running the programmer, recording and playing back through the session, and all the live control. show gate says plainly that the console is an RFR and how many rows it has held. To own a show on that machine, relaunch it as a full Command.

An RFR comes up blank — no fixtures, no presets, groups or executors of its own, whatever that machine held last time — and takes the host's show whole the moment it joins. It never writes a show file: nothing it adopts is saved under the host's name on its own disk, and it never mints an Untitled of its own. Your grand master and programmer are live control, not show data, and come back as they were.

Your tile layout and bezels are yours, on every machine. They live with the console, not with the show you happen to join: join a show, do it, come back and join again, and your tiles, bezel keys and saved layouts are exactly where you left them, whether or not the LD changed the file in between. A machine that has never had a layout — a fresh install — takes the host's tiles and bezels along with the show, and from then on they are its own. A show you open yourself from Load Show still brings back the views it was saved with.

Which network card

Settings ▸ Comms ▸ Network lists the machine's live interfaces; pick the one the show rides on. That choice governs where this console sends. The wire never uses a loopback address — that is a hard rule, not a preference.

Moved the console to a different network?

A console remembers the address it last talked to Babel on, so carrying it to a new network leaves it calling an address that no longer exists. New Show re-anchors it: it re-reads the chosen interface's live address, leaves the old session and reconnects. If the interface has no real address it changes nothing and says so, rather than falling back to loopback. After a network change, restart the whole stack rather than switching interfaces live.

Getting light out of the building

Physical lighting output — sACN and Art-Net — is Babel's job, not the console's. You configure and arm it either from Settings ▸ Comms ▸ Babel Protocols ▸ Lighting Egress or from the command line; the page composes the very same line, so the two are one route. Babel validates and answers either way, and the page prints that answer under the buttons.

On the page, pick the protocol, then work through the three groups — Output (which output and which universes), Destination (where the frames land, on which wire, at what priority) and Options (enabled, fan-out). The composed line, Apply, Arm and Disarm stay below the groups at all times, so you always see the command before you send it. The page is the two egress folds and nothing else — the session picture lives on its own tab, Babel Map, next door.

Babel Map

Settings ▸ Comms ▸ Babel Map is the map Babel itself draws, on the console: the broker at the centre, every connected app (Command, Light, Babel) on the inner ring with its name, role, domain and PNCLI / PN ports, and every piece of gear (ATEM, VISCA cameras…) on the outer ring with its address and universe. Solid links are apps, dashed links are devices. Pinch to zoom (40 % to 600 %), drag to pan, or use −, + and Reset above the map. With no session joined the map says so and waits — it fills from Babel's roster the moment a session forms. Two things Babel's own map shows are not drawn here yet, because the wire does not carry them: the green/red device liveness dot and the render frame-rate line.

egress sacn 1 map=1:1 mode=multicast prio=100 nic=en9 enabled=1
arm sacn 1
disarm sacn 1

The number is the output, not a universe. Configuring an output that does not exist creates it — disarmed — so follow it with arm. Leave the protocol word out and the console assumes sACN; give it a word it does not know and it refuses rather than guess, because guessing wrong configures the wrong wire.

KeyMeaning
map=<in>:<out>,…Which console universes go out as which wire universes. Up to 1024 pairs, each input and output used once. This wins over the block form below.
in= count= out=The same thing as a contiguous block. count must be 1–1024.
mode=multicast or unicast for sACN; broadcast or unicast for Art-Net.
dest=<ipv4>The receiver's address, when unicast. A loopback or all-zeros address is refused as you type it.
prio=<1-200>sACN priority. Art-Net has no priority field and will tell you so.
nic=Which interface to send on — a name, a role or an address. Node-local; it never travels in a show file.
enabled=0|1 · fanout=0|1On or off; fan the same universe to several destinations.

Mistype a key and the console suggests the right one rather than silently ignoring it — host points at dest, universe at map, priority at prio.

arm starts the stream; disarm stops it cleanly — sACN sends three stream-terminated packets so receivers do not sit on the last frame.

No armed lamp yet

Command has no indicator showing which outputs are armed. Babel's answer to your arm lands on the status line, and Babel's own window is where the armed state is visible.

Shows

show new [<name>]     start empty, under that name
show save            save the current show
show list            what is saved
show load <name>     load one
show export          export it, media included

New Show, Save Show and Load Show exist as bezel and tile actions too, and all three sit on the Show card in Settings ▸ Comms. Your detached windows and your workspace layouts travel with the show; a window pinned to a monitor that this machine does not have stays configured and closed.

Starting a new show

Press New Show — the bezel key, the tile, or New Show… on the Show card. A sheet asks for a name (already filled in with the next free Untitled) and tells you what will happen before anything happens. Confirm and Command saves the show you are leaving first, then clears the patch, the presets, groups, executors, timecodes and FX pools, the programmer, and your tiles, screens and bezel assignments — the same clean start the launcher gives you. The new show is written to ~/Phantos/Shows straight away, so it is on disk before you patch a single fixture.

Light's outputs stay as they are. A new show clears this console's document; it does not touch a Light node's outputs, and it will not open or close anything on a display. If you want an output gone, remove it on Light.

Settings, category by category

Comms ▸ Session has Broker, Session, Identity, Network, Priorities, Show, Launch and Install tabs. These also appear in the Sessions bezel window. Tabs remain available when the window is locked; changing a setting still requires unlocking it. In Priorities, choose a domain to inspect or adjust its priority. Choosing a tab or domain does not change a setting.

In Comms ▸ Babel Protocols ▸ Lighting Egress ▸ Output, map a sequential block with PN start universe, Quantity and Target start. For example, PN 7, quantity 16, target 401 maps PN 7–22 to sACN 401–416. sACN targets start at 1; Art-Net targets start at 0. Apply validates the block before sending it. Leaving all three blank keeps the existing mapping; for a partial block, omitted values use PN 1, quantity 1 and target 1 (sACN) or 0 (Art-Net). Nonsequential mappings remain available through the lighting egress CLI.

Every Settings page is built the same way. The six categories are tiles across the top. Below them, each subject is a card: a choice is a row that lights green when it is the one in force, a number has a − / + pair, a value you type opens the on-screen keypad when you tap it, and read-outs sit in dark capsules. Everything is a full-size touch target.

Gamepad camera holds

Camera and Followspot share Live Op priority above the normal programmer, with separate holds and pad undo history. Camera Focus also sets the profile’s manual-focus gate in that same layer. Console Clear and Release leave those holds alone. Turn off Camera mode or disconnect the pad to release that pad's camera holds. A pending autofocus reset cannot bring a disconnected pad back into control or replace a newer input.

Starting a new show or accepting a show load discards the previous show's live camera holds, camera fades and pad undo/redo history. Saved controller maps and camera positions remain saved. A refused load leaves the current holds intact. A Cam Start gesture is cancelled if its target, mode or binding changes, or the pad disconnects. Shift bindings use the active layer.

Switcher mode is retired. Existing Switcher assignments migrate to Programmer; saved Cut, Auto and FTB actions become ordinary held parameter bindings. HOTAS keeps Camera plus Programmer by default. ATEM fixture controls and tally remain available.

DS4, wired Xbox and GameController trigger button bindings fire at half pull. Held actions release their original targets when the pad changes mode, cursor or map, or disconnects. Absolute triggers can return all the way to zero; an untouched trigger does not claim a value. Fine and other held modifiers use the active Shift binding. Stick parameter bindings offer Y absolute or X velocity nudge. HOTAS throttle, twist and paddle honor their offered parameter methods.

DS4 followspot

Use an ordinary moving light with a correctly mapped Pan and Tilt. In Settings ▸ Gamepad, choose Use DS4 Followspot layout on the connected pad, then assign the lights you want. This replaces that pad's current bindings with the spot layout. Prepare the look and light output on the programmer before Grab; Grab does not home the lights or open the beam. Missing optics stay unavailable.

Release transfers the held look into the programmer before letting go, including Beam Clear values still held. The light keeps its aim; the programmer now contains an ordinary, undoable edit that can be recorded or changed. It does not return to the old pre-grab position. Turning off Followspot, changing its assigned set, or disconnecting the pad performs the same handback. Normal programmer Clear/Release does not drop a spot hold. Pad Undo/Redo uses the same isolated journal as Camera, including Beam Clear toggles. A new show discards it; press Grab again in the new show.

On Release, running programmer effects on the held attributes are stopped for those lights, so an old movement does not restart over the position you just left. Other effect targets and attributes keep running. Recall an effect explicitly to run it again; programmer Undo restores values, not stopped effects. A competing console's higher physical dimmer can take effect again under normal HTP merging after Release.

The Followspot setup shows the held set, active light and unavailable controls, with separate Pan and Tilt speed, acceleration controls and per-light iris reversal. Motion accelerates to stick speed without a queued target; centre stops immediately. After changing pad modes while controls are deflected, centre/release the controls before working in the new mode. A DS4 report outage stops further pad movement after 250 ms while retaining the last position. The separate Camera Follow video-overlay idea is not part of this mode.

Stream Deck

Plug one in; it is detected live, and Settings ▸ Deck shows the model, its key count and its serial. The last key or pedal you pressed is shown live, so you can prove a surface is talking before you map it. Brightness is a fader with a − / + pair beside it.

A key deck runs in one of four layouts — tap the one you want in the left pane and configure it on the right:

ModeLayout
ProgrammerEach row is a kind of thing — presets, groups, fixtures, tools — one item per column, with paging when a row overflows.
PlaybackEach column is an executor, each row an action: Go +, Go −, Toggle, Flash, Release. Flash holds while the key is down.
ATEMEach row is a bus — program, preview, the auxes — with direct input selects, plus downstream and upstream key rows. Keys light from real tally.
KeypadA command keypad with a live banner showing the line you are typing.

Keys are assigned in Settings ▸ Deck, not on the deck itself: choose Keypad mode and tap a key in the on-screen grid to pick what it does. The deck repaints as you go. Named layouts can be saved, loaded and reset to factory.

A Stream Deck Plus is different: its eight keys are the attribute-group bank mirroring the on-screen Programmer panel, and its four dials are per-attribute faders for the group you picked. Pressing a dial holds fine mode; tapping a segment of the touch strip homes that attribute to its profile default. Switch it to Playback in Settings ▸ Deck, or hold the first and fourth dials together (the second and third bring Programmer back), and it becomes the playback desk: four keys pick a Rate/Width pair, the first dial sets that pair's rate and the second its width, the third dial is the programmer fade, the fourth is the Grand Master. SPLIT lets fade-out differ from fade-in (hold it and turn the fourth dial), FADE toggles the fade override, FULL restores the Grand Master, and FLASH is full while held. Press the first dial to tap a tempo into the pair; hold the fourth dial down for a blackout.

On a key deck, a row whose pool is empty names itself on its first key — no presets, no groups, no fixtures, no execs, no ATEM — instead of a wall of black keys that reads like a dead deck.

A foot pedal has three switches — left, middle, right — and each fires a command line of your choosing on the press. They start as go 1, release and clear. Bind one to shift and it holds fine mode instead of running anything. A binding must be a command line the console recognises — a sentence for the mind is refused with the console's own hint and the switch keeps its previous binding; a pedal never talks to the mind. Your clear, release, undo and redo act on this console only — only mclear / Master Release cross to every console.

If a deck will not open, macOS is the usual reason: System Settings ▸ Privacy & Security ▸ Input Monitoring, enable Phantos, relaunch. The console prints exactly that when it happens.

Deck limits worth knowing

  • The keypad grid is laid out for an XL (eight by four). A smaller deck will not match it.
  • First-generation Stream Decks and the Minis dispatch correctly but their key images stay black.
  • What you type on an XL keypad is its own buffer — it does not appear in the on-screen command line.

Talking to the desk

Tap the microphone beside the command line and speak; tap again to send. Hold the pad's push-to-talk button, or speak on an armed comms channel, and it is the same path. A spoken ask goes to the AI lane, which answers with a proposal — the exact commands it would run, shown to you verbatim.

Nothing runs unconfirmed

A proposal sits there until you accept it — proposal run, the Run button, or ending the spoken sentence with the word engage. proposal dismiss throws it away, and keying the microphone again dismisses it too. There is deliberately no keyboard shortcut on Run: a stray Return must never put a proposal on stage.

On a comms channel the console cannot hear you key up or key down — it hears only sound starting and stopping — so it waits out a silence before deciding you have finished. Say engage and it stops waiting: the word ends the sentence, so the desk submits the moment you stop talking rather than sitting through the pause. The desk hears the word through its usual mishearings, so gauge or engaged still close the sentence. Anything you say WITHOUT that last word is a proposal and nothing more, and it still gets the full silence window — think mid-sentence for as long as you like. Set that window, and the channel's sensitivity, in Settings ▸ Audio.
